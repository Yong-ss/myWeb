## 1. 项目目标

在现有「四方联赛 V1」已经上线的基础上，为《诡秘之主》新增「高原竞逐」赛事管理；优先复用身份匹配、双表合并、编辑补录、版本历史、权限隔离、俱乐部玩家 UUID 等基础，活动专用数据契约、字段、筛选与出勤口径分开。

工作流原则：外部视觉 AI 读取游戏截图 → 结构化 JSON → Club 核对身份及纳入范围 → 保存单场战绩。暂时不开展 OCR / 浏览器端 PaddleOCR 开发。

## 2. 已确认业务规则（用户直接确认）

- **参赛判定**：高原竞逐排行榜只要出现该玩家的名字，即代表他实际参加，即使所有统计数据为 0；所有为零的行也要保留为参赛记录。
- **场次单位**：排行榜数据对应**单场比赛**，每打一场产生独立战绩；不是当日或阶段/赛季累计。
- **组织结构（此前用户介绍）**：四个势力，每个势力包括多个俱乐部；高原截图可能混有其他俱乐部参赛者，网站的俱乐部战绩只应纳入本俱乐部的玩家。
- **截图收集方式**：玩家使用 Windows PC 游戏客户端截图。
- **当前阶段**：仅讨论、文档化、核对规则，暂不开发；讨论文档经用户同意已加入 main，历史工作分支保留。

**注意**：「排行榜没有该玩家」不能单凭截图缺失认定该玩家缺席；可能仅仅没拍完整。参赛肯定证据和缺席证明应区别处理。

### 5.1 已确认的参赛与统计含义

- 排行榜出现姓名即为参加，**全零仍记参加**；两表顺序可不同，按已核实的玩家 UUID 合并，不可按行号拼接。
- 没有出现在已完整核对的比赛数据里的成员，才可能依据该场成员资格计算缺席；不能因为 AI 没识别到人就立即判缺席。
- 从当前已知截图看，输出应包含「击败、助攻、消散、唤醒、战功」，战略应包含「对玩家伤害、承受伤害、治疗、净化」，**高原不含守卫伤害**；字段归类/名称的最终 JSON 契约待定稿。
- 总积分由管理员手动录入；个人战功是独立指标，不能擅自当作积分。势力从四个固定选项中手动选择、名次手动填写且限制在第 1～4 名；**势力与名次均允许留空**，填写时必须校验。名次表示**该势力在本场四个势力中的排名**，不是本俱乐部排名；四个势力的完整官方名称仍需核对，不能臆造。

## 6. 重点实现方案（建议，尚待最终批准）

### 6.1 最核心：整个势力的截图如何准确筛出自己俱乐部

**不能把匹配成功等同于身份和当场成员资格已经获得游戏证明**：高原截图只有势力列，没有俱乐部列或 UID。推荐导入流程：

1. AI 对**整个势力**的「输出」「战略」全部可见玩家和指标按原图提取，不让 AI 预测谁在本俱乐部，也不要只让 AI 猜测性输出「自己人」。
2. 网站读取**最新 Club 成员名单 + 已确认昵称别名**，以精确昵称／已确认别名形成「本俱乐部候选」。相似昵称只提示候选，不自动纳入。
3. 预览把原始来源行分类为「拟纳入本俱乐部」「拟排除外部」「待人工确认」；**必须允许管理员手动改纳入／排除、改绑和补充历史玩家**。自动匹配不等于已证明同名玩家身份。
4. 输出／战略分别匹配，再按最终确认的本俱乐部玩家 UUID 配对；固定本人行和滚动重复行要按来源、字段一致性审查，不能无条件消去同名不同人。
5. **仅当本俱乐部纳入者的双表都齐全、数字均合法、待确认问题已解决后，才能正式提交**。页面展示纳入人数、排除人数、未解决数和最终对照清单。
6. 数据库存储已确认的本俱乐部参赛者（含原图识别昵称及允许保留的来源字段）。完整跨俱乐部 JSON 在浏览器核对阶段使用，**不持久化外部玩家原文**；如果需要审计，设计保留仅本俱乐部记录的来源 JSON 与原始筛选决策摘要，不能把删减版伪称为「未经修改的原始 JSON」。
7. 服务端重新校验场次类型、目标俱乐部、每名玩家 UUID 属于该俱乐部的**身份档案**、双表配对、数值、权限及并发版本；前端勾选并不是可信授权。注意：Club UUID 属于档案不自动证明在比赛日仍在会。

### 6.2 四方安全边界与多赛事隔离

- 共用登录、Club 玩家 UUID、昵称/别名匹配、赛事主生命周期、手工 CRUD、版本/审计/幂等和事务隔离。
- **赛事列表／详情／单人参加和缺席统计／日期查重／权限均按活动类型隔离**；四方旧接口/旧链接只能返回四方内容，不能让原四方统计误把高原记录算进去。
- 单独设计高原 `read/import/edit` 权限，并相应更新平台/联盟权限层，保留俱乐部隔离与原始来源可见性原则；具体键名待开发前固定。
- 高原指标字段另定义，不许拿四方「对守卫伤害」强制填 0。可以先评估扩展现有明细表还是为高原独立建指标明细；**不复制整套认证权限/版本系统**。
- 所有改动必须新建增量 Supabase migration；已上线的 `20261104140000_club_events.sql` 不得回改。正式 DB 迁移遵循备份、演练、校验、发布顺序；本轮不执行任何迁移。

### 6.3 最新名单与历史快照：最需警惕的数据正确性

用户明确要求「匹配按最新 Club 名单」，同时「战绩一经保存不因退会改变」，以及「缺席按比赛当时在会人员算」。

**推荐区分三件事：**
- **导入候选**：使用导入时最新已同步名单与已确认别名，并允许管理员为历史已退会参赛者手动关联旧档案。
- **保存的参赛快照**：本场纳入 UUID 和数值持久化；以后成员加入/退会、昵称更名，都不影响此前确认的参赛事实。不要定期按最新名单重算或删除旧战绩。
- **缺席证据**：应以比赛日期可证明的在会/有资格记录为依据，**不能用查看页面当天的最新名单倒推过去的缺席**。没有足够成员历史证据时列「资格不确定」而非记缺席，沿用四方保守原则。

用户已明确同意：允许手动选择历史退会玩家进行过去战绩补录；历史成员资格证据不足时不记缺席、显示「资格不确定」。这与最新名单作为**导入候选来源**并不冲突。

## 7. 四项边界全部已确认（2026-11-05）

用户对上一轮四条建议逐项**全部同意**，据此固定以下业务规则：

1. **历史比赛补录／已退会成员**：允许在赛事导入／编辑的身份核对页手动搜索、选择历史玩家档案，关联其比赛时的参赛数据；不会因为现在已退会而删除或拒绝保存以前的战绩。最新名单优先作为导入候选，但**并非唯一身份来源**。
2. **保守缺席认定**：只能凭比赛当时的成员历史证据判定在会/资格；如果比赛当天完整成员记录缺失，不能以今天最新名单倒推旧比赛缺席，显示「资格不确定」，不计入缺席次数。参赛记录一旦确认，仍正常计参加。
3. **势力与名次**：势力选择使用**四个固定游戏势力选项**；本场名次是**本势力在四个势力中的排名**，限 **1～4**；两项都允许留空，可手动补录或修正，修改应走版本/审计。**四个势力的完整官方名称尚未收到，不得臆造**。
4. **全势力筛选最终人工确认**：精确昵称／已确认别名匹配只生成「拟纳入」候选，不自动宣称游戏中的玩家归属已证明；管理员在每场保存前必须明确确认**最终纳入本俱乐部的名单**。外部同名或 AI 误名不能凭纯昵称保证 100% 准确。

以上四项已纳入 V1 需求，**不再作为开放的 A/B 问题反复询问**。此确认不等于批准开始代码开发或生产变更。

## 9. 四方联赛开发复盘与高原架构评审摘要（2026-11-05）

> 来源：Codex 对四方联赛需求文档、主要实现 commit `6955640`、后续 Git 历史、现有源码/测试及高原需求的只读分析；本节是**复盘与方案评审，不等于用户批准开发**。本次对关键代码另作核对：当前 `contract.ts` 数值解析含 `Math.round`；`club_events.event_type` CHECK 仍只允许四方；`club_player_events` 仍未按类型过滤；CI 工作流未见直接执行 `test:compat`。

### 9.1 一句话结论

**保留四方 V1，增量支持高原。共用赛事主表及成熟的身份/版本/事务/审计能力，高原新设专属指标明细与独立权限；仅小步提取两边实际共用的组件，不先进行全系统重构。**

### 9.2 按业务重要性排序

1. **P0：混合势力筛选正确性。** AI 提取全势力双表，按最新 Club 名单/已确认别名生成拟纳入候选；相似/同名/历史成员须人工确认；最终确认本俱乐部名单。仅本俱乐部来源数据提交并持久化，外部玩家原文不能泄漏到原始保存列、审计或日志。无游戏 UID 时，机器只能辅助，不得声称 100% 证明玩家归属。
2. **P0：赛事类型隔离。** 四方旧列表、详情、版本、编辑、个人出勤、缺席、日期查重、权限接口必须限定四方；高原独立权限与路由，不能继承现有 `events.*` 授权。新旧类型交叉必须在数据库侧拒绝。
3. **P0：兼容上线。** 旧四方表结构与历史保留；高原单独指标表，主表允许两种活动，数据库强制父子赛事类型一致；只增加新 migration，验证旧 Worker + 新数据库兼容，以及从未修改四方历史数据。
4. **P1：高原完整记录与便利编辑。** 单日最多一场；双表只对**最终纳入本俱乐部的玩家**强制一一对应，外部玩家的缺表不应阻止本俱乐部保存。高原个人战功和无守卫伤害，手填本俱乐部积分、可留空的四选一势力与势力名次（1～4）；**纳入本俱乐部参赛人数必须至少 1 人**；复用单场 CRUD/版本/改绑与全零指标也算参加的规则。
5. **P1：可靠个人历史。** 已确认的参赛 UUID 不因退会改变；缺席按比赛日成员历史推导，证据不足显示资格不确定；四方/高原不能混计。
6. **P2：有针对性的四方小修补与测试。** 来源映射与服务端校验范围、字符串小数被 `Math.round` 静默取整、首批 100 场日期预查、身份查询静默上限、同名同值去重策略及 CI `test:compat` 缺席。先证明存在具体影响，再实施最小兼容修复，不以此为由全面重构。

### 9.3 值得采纳的技术设计（**建议，未经最终开发批准**）

- **赛事主表共享，指标明细按活动类型独立**：保留 `club_event_players` 四方结构，新增例如 `club_highland_event_players`；服务端校验高原明细绝不能链接四方主赛事，反之亦然。
- **输入与审核流程分开**：高原使用专属 AI JSON 格式；全势力数据先在浏览器内完成过滤、双表匹配和异常审查，再发送白名单后的本俱乐部记录。服务器可证明请求内部一致性，但不能证明游戏昵称对应真人。
- **核对体验**：先显示「本俱乐部拟纳入玩家」及异常/可疑遗漏，外部玩家折叠、可搜索、支持批量确认，避免逐个审核数百条外部记录；最终保存前人工确认纳入名单。
- **抽象边界**：小范围共享身份候选、指标控件、排序表格、版本展示；不引入动态任意活动字段引擎、万能导入系统或完全重写权限。
- **测试发布顺序**：先建四方类型隔离和回归测试 → 增量数据库及权限设计/兼容测试 → 高原纯逻辑与 UI → 真实集成和浏览器 E2E → 备份/演练迁移/CI 发布。

### 9.4 仍需在工程契约中明示，而不是重新问已确认业务规则

- **高原本俱乐部无人参赛**：**已确认不允许保存人数为 0 的比赛**。创建和后续删除/改绑/补录均需维持有效场次至少 1 名本俱乐部参赛者；全零统计的参赛者仍算 1 人。因为 0 人场次不可保存，网站不能仅凭那场未保存的比赛自动产生缺席记录。
- **全势力 JSON 体量**可能超过四方单表 300 行或 256 KiB，需用真实样本评估容量，但正式保存仍只提交本俱乐部记录。
- **势力名称和元数据**：四个固定势力的准确名称须依据游戏截图/用户提供；**势力与名次均允许留空已确认**，填写时校验四势力/名次 1～4；编辑后必须保留版本与审计。
- **来源校验**：如果用户已确认排除某外部玩家，外部行只缺一张表不能阻碍保存；对纳入者的数值缺失、双表 UUID 不一致仍阻止保存。服务端校验保留来源与最终 UUID 映射，**不得假称验证它未收到的整份全势力 JSON**。
- **现有 CI 全绿并不代表兼容测试已运行**；务必显式覆盖旧 Worker 与新 DB、新旧权限隔离、历史参赛/缺席、来源隐私、并发及所有编辑动作。

本节不改已确认的游戏规则、不启动开发；所有技术方向均待用户最终审核和授权。

## 10. 最后三项业务规则已确认（2026-11-05）

> 本节覆盖 §9.4 旧的开放问题；这三项**不再视为未定需求**。

1. **至少 1 名本俱乐部参赛玩家才能保存正式高原赛事。** 如果整场势力榜中没有任何可确认属于本俱乐部的参赛者，禁止创建正式记录。禁止删除最后一位参赛者导致有效赛事人数变 0；可通过作废该场处理。**不要把全零指标误当成 0 名参赛者**。因为 0 人场次不保存，不能从不存在的场次自动计算缺席。
2. **势力、名次都为可选字段。** 势力在提供时须为固定四势力之一（完整官方名称待核对）；名次在提供时须为 **1、2、3 或 4**，代表当前选择的势力在本场的排名，而不是俱乐部排名。允许两项都未填写、只填写其中一项或随后通过授权编辑补齐；未填写按空值处理，绝不猜值或用 0 表示。编辑时保留版本与审计。
3. **高原和四方权限独立，但默认职位沿用四方。** 初始默认授权：**公会长（owner）和俱乐部管理员（admin）可读、导入、编辑；联盟会长（alliance_leader）只能读整理后的战绩**，受直接俱乐部/联盟读取边界限制；平台管理权限沿用相同控制原则但必须独立管理高原授权。高原独立权限键（建议 `highland.read/import/edit`）的覆盖/例外必须**独立于**四方 `events.read/import/edit`，不能复制或继承四方用户已有的个别授权。读权限是高原写权限的前置。超管/平台角色与安全封顶继续按现有权限系统边界实施，不因新增活动获得额外数据访问。

### 开发契约与测试验收关注点

- 导入处理后只有 0 名纳入玩家、最后一人被移除、全零参赛者、两张表遗漏、同名误纳入等分别有明确拒绝/允许测试。
- 势力和名次：均空、一空一填、四个合法选项、1～4、非法势力、非法名次、补录修改与版本回放，都要有前端/服务端约束和测试。
- 权限矩阵：owner/admin 默认可读写，联盟会长只读；四方授权或显式拒绝不得直接影响高原，反向亦然；无高原权限不能通过四方旧 API/RPC 编辑或读取高原赛事。
