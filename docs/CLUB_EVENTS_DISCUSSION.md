## 0. 开发前最终静态审核（2026-11-04）

**审核范围**：已有四方联赛产品讨论、V1 JSON/Prompt、现有 Club 身份/历史 API、权限 SQL、导航和 `docs/TESTING.md`。这是**代码和规格的静态检查**，不是运行测试或部署；旧的讨论语句与本节冲突时以用户后续确认决定及本节工程安全边界为准。原始决定可在 Git 提交历史核对。

**结果：核心业务规则已经闭环，用户不需要再回答字段名、排序或同一问题的 A/B 选择。** 下面这些实现风险必须在 Codex/Claude 开发时处理：

| 发现的风险 | 必须采用的做法 |
|---|---|
| 平台管理员无法沿用现有个人权限储存 | `club_permission_overrides.set_by` 目前仅有 `super_admin` 和 `owner`（`20261101195800_club_permission_layers.sql`）。平台管理员赛事管理需新增**仅限三项赛事权限**的受限层/RPC/审计，绝不可伪造超管来源或获得 `platform.permissions.manage`。 |
| 权限层互相覆盖 | 计算顺序：系统安全 → 超管职位上限 → 超管强制值 → 平台个人赛事设置 → 平台俱乐部职位赛事设置 → 公会长管理员设置 → 默认。三态允许/禁止/跟随；撤销回退当前下层；平台不能给自己加权。按现有 `permission_layer()` 和 Worker/RLS 实现及测试。 |
| 原始 AI JSON 泄漏给联盟会长 | 联盟会长只能看整理后的赛事战绩。原始 AI JSON 必须校验**直接俱乐部**赛事读身份，不可以借包含联盟的 `can()` 阅读；RLS、Worker、导出均遵守。 |
| 赛事读/写绕过其他权限 | 仅有赛事权限不自动拥有 `members.read` 或 `aliases.manage`；本场选择 UUID 可以，但未经别名权限不能把 AI 错名保存到全俱乐部别名库，身份搜索仅返回最小必需信息。 |
| 缺席错误地按全部历史比赛扣分 | 个人只统计经成员历史证实在会且未参赛的有效场次。暂离、不确定、入会前、退会后、同日入退会先后不明不计缺席；有完整双表记录即使指标全 0 仍算参加。不可只用玩家历史页面第一批 100 条资料计算。 |
| 玩家个人资料链接日期问题 | `ClubScoreTrend.tsx` 和 `MembersPage.tsx` 会带 `date`，`PlayerHistoryPage.tsx` 会使用它截断查询；改为仅 `id/club`，并忽略旧书签的 `date`，保持原评分日期对比。 |
| 同场修正导致计数不一致 | 删除某参赛者要删该场**输出+战略**整条，不能删除档案；身份 A→B 若 B 已有战绩先阻止，再明确人工删除错误行。每次新版本自动重算参赛人数、总击杀、参加/缺席；最后一个参赛者不能被删成空比赛，应作废整场。 |
| 日期并发、作废/恢复或重放导致重复 | DB 对有效 `club_id+event_type+date` 建部分唯一约束，UUID 稳定；事务内校验期望版本、权限、双表完整，重复请求 ID 幂等，冲突 409，不留下半套战绩或孤儿新档案。 |

**注意**：§6.2 的 JSON V1 字段名和 §6.2.1 的豆包 Prompt 已属工程定稿，但目前未编码、未真正执行导入测试。交接时要覆盖：错名/重名、两表乱序、重复固定悬浮行、`50.1万` 换算、`null`、缺行、历史玩家、新建身份、越权、并发、作废恢复、个人统计及旧链接回归。成功经过真实隔离测试库与浏览器 E2E 后，才可以宣称「录入正常」。

**发布风险**：按 `docs/TESTING.md`，向 `main` 推送代码可能自动部署，Supabase 迁移需人工执行，旧 Worker 与新 DB 的过渡须通过兼容测试。**此阶段不允许改变 main、生产数据库、应用代码、Worker 或部署**；仅这份讨论分支文档。

## 2. 用户提供的四方联赛截图（直接观察，不代替游戏规则确认）

两张截图顶部均为「势力排行」「数据统计」，右上角筛选值为 **「千秋｜君辞赋」**。左侧有四个俱乐部的排名条目，但 **V1 只关心自己指定的俱乐部**。示例截图中「千秋｜君辞赋」显示积分 **3000**、击杀 **131**（仅为这场截图的数值，不是预设值）。

### 俱乐部整体成绩（已确认）

- **每场只管理本俱乐部的总积分，以及按该场参赛玩家「击败」字段自动汇总的总击杀**；另外三个俱乐部的排名、积分、击杀等数据一律不需要录入或保存。
- **总积分由管理员在创建赛事时手动录入**，保存后可从赛事详情单独修正并保留历史；**总击杀不再手动录入**，而是由该场已确认玩家数据自动计算。无需强制站外 AI 识别左边榜单；个人统计仍可使用截图 → 外部 AI → JSON 的路径。
- **用户现已明确决定使用个人「击败」合计作为网站展示的「总击杀」指标**，取代之前「口径未确认/手填总击杀」的要求。它是站内定义的汇总口径；如与游戏左侧榜单显示的「击杀」不一致，不得擅自宣称两者为相同的游戏官方统计口径。
- 俱乐部总体成绩应关联到对应的一场四方联赛，而不是作为所有场次共用的固定字段。

### 截图一：「输出」标签

表头为：**玩家名字、俱乐部、击败、助攻、消散、唤醒**。

- 用户确认右上角可以**指定筛选查看某一个俱乐部**；本例选择「千秋｜君辞赋」，当前可见玩家行的俱乐部均显示为该俱乐部。因此无须采用高原竞逐的「从混合势力中逐个挑选自己俱乐部」流程。仍需以最终导入内容/页面核对筛选结果，不能仅依赖 AI 推断。
- 例：玩家「北忧」的数据显示击败 9、助攻 26、消散 0、唤醒 0。
- 当前截图为滚动列表的一部分，不能凭此断定全部玩家都已拍到。
- 底部另有高亮固定的「北忧」行，看起来与列表内「北忧」的数值相同；**解析时应避免把固定展示行当作第二个人，但重复行判断规则仍待核实**。

### 截图二：「战略」标签

表头为：**玩家名字、俱乐部、对玩家伤害、承受伤害、治疗、对守卫伤害、净化**。

- 例：「北忧」的数据显示对玩家伤害 50.1万、承受伤害 19.9万、治疗 0、对守卫伤害 452.7万、净化 0。
- 此截图中的「输出」和「战略」分类及其字段，以**四方联赛截图的实际标签**为准，不沿用此前其他活动截图的字段归类。
- 「万」等数值单位需要在未来 JSON 契约中统一处理；缺失或无法识别不能擅自填 0。
- 两页排序不同；**不能按排行榜行号合并两页数据**。

### 目前可合理讨论但未批准的做法

- **已确认可在游戏界面按俱乐部筛选**。建议先在游戏里选择目标俱乐部，再把两类结算截图交给站外 AI 提取 JSON，网站核验 JSON 的俱乐部名称与当前选择是否一致；避免重新做混合势力的复杂过滤。要保留对昵称差异、历史成员与重复记录的核对。
- 两份数据应在确认是同一场活动、同一位玩家后合并；匹配优先考虑昵称与现有玩家 UUID / 已确认别名，发生冲突时人工核对。
- 不改变现有每日成员 JSON 格式；四方联赛采用独立的 §6.2 V1 JSON schema 和 §6.2.1 站外 AI Prompt，字段名为本项目工程契约，前端解析、后端验证和 Prompt 必须完全一致。

### 现有昵称识别能力复用评估（2026-11-04，代码已检查）

**用户实际经验（已确认）：** 近一周使用豆包识别每日成员数据时，数值识别错误极少，主要遇到的是昵称识别错误。四方联赛希望优先复用已有的昵称核对能力；这只是实际使用经验，不能假设 AI 数字永远不会识别错。

**代码检查结果（现状，不代表已经实现到四方联赛）：**

- `apps/club/src/features/import/identity.ts` 已有 `matchPlayers()`：正式昵称唯一精确匹配、已人工确认的别名匹配可自动定位玩家 UUID；Unicode NFKC / 去装饰符号 / 有界编辑距离只用于提示候选，**不把相似昵称直接当成同一人**。
- 同名玩家、别名冲突、同批昵称重复、多行指向同一 UUID 会停止自动关联，交由人工确认；已归档玩家仍可按身份档案匹配。对应测试见 `apps/club/src/features/import/identity.test.mjs`。
- `ImportPage.tsx`、`IdentityDialog.tsx` 已有候选列表、手动选已有玩家、必要时新建玩家、改正昵称、可选择「记住 AI 错名」、最终核对等界面；`worker/imports.ts` 从俱乐部范围的 identity context 获取玩家和别名，后端也负责确认与数据校验。
- **可以复用身份匹配规则、玩家 UUID、经确认的别名及交互模式，但不能直接复用整份每日导入 JSON 契约和所有页面逻辑。** 现有 `matchPlayers` 接受每日 `Member`（含等级、途径、入会天数等），其历史数值异常检测对四方联赛没有适用依据。开发时应抽出/适配通用「按昵称匹配玩家」核心，赛事字段另外建 schema；每日名单的缺席核对、替换完整成员名单等流程也不应触发。
- 四方联赛「输出」「战略」是**同一场比赛的两个统计来源**：先分别保留原始昵称及数据，依据已确认玩家 UUID 合并，不能按行号/排名合并，也不能把两张表简单拼接后交给现有的「同批重复玩家」逻辑，否则同一玩家在两表出现可能被误判为重复。
- 昵称识别不一致、匹配到多个候选、同一张表重复玩家等情况，只呈现异常核对；已匹配的玩家可以在最终预览快速复查。若名单尚未同步，仍允许管理员明确选择「新增/关联历史玩家」，但**不能仅因未匹配到当前成员就擅自新增玩家或判定退会**。
- 单位换算（如「万」）、数值非负、漏字段（缺失不能自动当 0）、相同赛事重复导入等轻量校验仍应保留；数值允许在预览中更正作为保险，但无需为很少发生的数字 OCR 错误设计复杂 AI 纠错流程。
- 建议优先为四方联赛身份匹配增加测试：输出与战略昵称一致/不同、已确认别名、同名冲突、重复固定行、历史成员、尚未同步新人、错误昵称纠正以及两个标签顺序不同。**这是推荐实施方向，尚未获得开发授权。**

### 单条记录修改：现有每日导入功能的准确复用边界（补充复查）

**用户指出的现有功能确实已经存在，不能当成全新功能重新设计。** 已复查 `ImportPage.tsx`、`IdentityDialog.tsx`、`contract.ts`、`workflow.ts`、`worker/imports.ts`、相关 SQL 及浏览器测试：

- **导入预览阶段**：每条记录可独立展开、搜索及重新选择已有玩家/新玩家，修改识别昵称及其他字段，移除/撤销移除行，确认后进入完整预览；AI 原始昵称单独保留，明确选择时可记住错名关联。昵称更正既有档案也有专门交互，最终提交前不写库。
- **已保存当天数据的局部修正版**：再次选择同一天并提交 JSON 时，页面有「只补充／修正部分玩家（merge）」与「重新导入整份名单（replace）」；merge 更新本批同一 UUID 的数据并保留未提交玩家，replace 则以本批为准；均保留旧版、进行确认/并发检查及审计。**这是现有的日期重新导入工作流，不是已经存在的「在已保存战绩页面直接点某条编辑」功能。**
- **需特别防止身份改绑残留**：现有 `mergePreview()` 与数据库合并逻辑按 `player_id` 保留旧行。假设已保存战绩错误绑定 A，后来只导入修正成 B 的一行，普通 merge 会留下 A 的旧行；四方联赛不可直接照搬此点，否则战绩重复。应在赛事专用修正事务中明确处理「旧身份 A → 新身份 B」并校验唯一性、保留可追溯版本（具体 UX/接口仍未批准）。
- 因此四方联赛**首选复用现有「逐条修正 → 核对 → 确认保存」交互与公用组件/身份能力**，避免重做。赛事两张表的跨来源合并与专用持久化模式另行适配；不引入每日名单的完整名册/退会判断。
- `tests/browser/nickname.spec.mjs` 已覆盖「更正昵称直到最终确认后才保存」；四方联赛应补充错误 UUID 改绑与不残留旧记录的测试。

**后续已明确决定（以 §5 为准）**：赛事保存后在赛事详情里直接编辑玩家两类战绩或身份、手动补录玩家，保留历史版本与审计；不需要重新导入整个 JSON。旧的「在两种编辑入口之间二选一」已解决，不再提问。

### 已澄清：赛事详情是单场参赛玩家的数据表，不是另建累计排行榜（2026-11-04 续谈）

- 用户明确说明：进入某一场四方联赛详情后，希望**像现有 Club 成员列表一样**，直接显示该场所有实际参赛玩家及其数据，复用现有表格 UI、搜索/过滤和可点击列标题的升序/降序排序箭头。不是要求另建「跨所有比赛累计击败排行榜」或每次询问退会玩家是否出现在一个额外排行榜。
- 同一场有「输出」「战略」两类数据视图（可用标签切换或等价布局），各自显示原始截图对应指标；参赛玩家身份以经确认 UUID 关联，切换视图不会丢失玩家、按不同排名行号错配。列表只覆盖本场实际参赛者（包含后来退会的历史参赛者及零数据参赛者），不强行展示未参赛的全俱乐部成员。
- 数值表头允许点击切换从高到低/从低到高；搜索和表头排序是**视图操作**，不能改变数据库战绩值、原始 JSON、玩家身份或对统计的计数。复用现有成员列表的表格、按钮与排序交互风格，不要开发不必要的第二套排行榜体系。
- 已另行确认的「玩家个人档案显示跨场次参赛统计」仍然存在，不能与上述**单场玩家表**混为一谈。是否将来增加独立跨场次排行榜属于未要求的新功能，V1 **不开发**。
- 此条为用户对产品意图的澄清，并不表示表格或赛事功能已实现。

## 3. 比赛日期与场次

### 已确认：日期手动选择

- 每场四方联赛的**比赛日期由管理员在 myWeb 导入/创建活动时手动选择**（日期选择器），不强制以 JSON 导入时间或当前日期代替。
- 此日期与本俱乐部该场的总积分、总击杀、个人「输出」及「战略」数据属于同一场活动。
- 支持补录过去比赛；**工程默认拒绝未来比赛日期**，由服务端按俱乐部本地业务日历（V1 默认 Asia/Kuala_Lumpur）验证。比赛日期是日期值，不带时间；未来日期不允许提前影响个人缺席统计。

### 已确认：已保存场次允许修改比赛日期（方案 A，2026-11-04 续谈）

- 用户选择 **A：可在该场四方联赛的赛事详情中修正比赛日期**，不必删除重导或重新上传 JSON。该操作属于「修改战绩」权限范围，且仍受「查看战绩」前置依赖和俱乐部隔离约束。
- **同一场保持原赛事 UUID 不变**，原有俱乐部总积分、参赛玩家 UUID、完整「输出」「战略」指标继续归属这场比赛；只改变其业务日期，不得凭日期变化创建第二场或让玩家战绩重复计数。
- 仅允许在同一个俱乐部内变更日期。保存前校验该俱乐部目标日期是否已有另一场有效四方联赛；**若已存在则禁止修改、提示日期冲突**，不得自动合并、覆盖、取代任何一场。并发修改也必须由数据库唯一约束/事务检查防止冲突。
- 确认保存时保留原日期、新日期、操作人、操作时间、修改前后的版本与审计。当前赛事列表、按日期过滤、个人参赛历史及统计以**最新有效日期和版本**为准；旧日期仅在审计/版本历史中可追溯，不作为另一场有效赛事。
- 已保存场次修改日期时，同样拒绝无效和未来日期。

### 已确认：同一天最多一场

## 3.1 四方联赛权限（2026-11-04）

### 已确认：独立于每日成员导入的权限

### 已从 repo 核实：四种管理身份实际不同，且存在需扩展的权限边界

- 当前固定职位共五种：**超级管理员、平台管理员、联盟会长、公会长、俱乐部管理员**。参考 `docs/CLUB_PERMISSIONS_PLAN.md` §1（2026-11-02 的已确认规格）及 `apps/club/src/components/layout/AccountControls.tsx` 的角色名称显示。

### 已确认：查看权限是赛事写操作的必要条件（方案 A，2026-11-04 续谈）

- 「查看战绩」是四方联赛「导入比赛」「修改战绩」的**必要前置权限**。管理员要实际执行导入，必须同时具有有效的「查看战绩」与「导入比赛」；要实际执行修改，必须同时具有有效的「查看战绩」与「修改战绩」。仅有查看权限仍不能导入或修改。

- 关闭查看权限**不自动清除或改写**其他两项原先的授权设置；以后恢复查看权限时，导入和修改仍按当时最新权限层级重新计算，而非自动无条件开放。
- 此规则只约束四方联赛的三项权限，不影响既有每日成员导入和普通成员资料查看；超级管理员仍遵循现有可信 MFA / 最高授权机制。
- **验收用例**：查看=否、导入=是、修改=是 → 赛事读取/创建/修改 API 均拒绝；查看=是、导入=否、修改=否 → 只读允许；查看=是、导入=是、修改=否 → 只允许创建导入，不允许修改已有赛事；读取禁止时不能借导入/修改接口取回赛事敏感数据。

### 已确认的实施路径（未授权编码）

1. **导入时直接关联现有玩家 UUID。** 复用 Club 已有昵称、人工确认别名、相似候选和逐行纠错机制；有争议时先人工确认，不凭昵称相似直接写入。游戏唯一 ID 不是截图必需信息。历史退会、改名玩家的战绩要保留，并不因为导入活动战绩就自动更改当前入会状态。

- 作废必须保留原赛事 UUID、原始输入、历史版本和审计记录；**可恢复**，恢复时应继续使用同一个赛事 UUID，不得复制成新比赛或重复累计。具体恢复入口、权限与冲突检查尚待确定。
- **已确认：作废释放日期占位（方案 A，2026-11-04 续谈）**：作废后，该场不再占用「同一俱乐部 + 四方联赛 + 比赛日期」的有效场次唯一名额，允许管理员在同日重新创建正确比赛。若随后尝试恢复已作废旧场次，但该日期已有另一场**有效**比赛，必须阻止恢复并明确提示日期冲突；不能合并、覆盖、替换或产生两场有效比赛。可追溯的旧场次和旧 UUID 均保持不变。数据库以仅约束有效场次的唯一性机制和事务并发检查落实。
- **工程定案**：作废/恢复都归已确定的「修改战绩」权限，且必须有「查看战绩」前置授权；继续要求操作确认、事务版本、审计，不增加第四项权限。此为规格，尚未实现。

### 已确认：俱乐部总积分修正与总击杀汇总（2026-11-04 续谈）

- **总积分**：创建四方联赛时由管理员手填；保存后具有「修改战绩」有效权限的用户可在该赛事详情直接编辑该场总积分，不需要删除重导或重新上传 JSON。修改须有确认、旧值/新值、操作者与时间审计，并保留修正前的有效历史版本；个人统计及其他场次不受影响。
- **总击杀**：不再让管理员手填，也不提供独立编辑；采用该场**最新有效版本**全部已确认参赛玩家的「输出 → 击败」数值相加，每个玩家 UUID 只计算一次。个人击败数据修正、身份冲突修复完成后，总击杀应自动重新计算；旧版本和审计记录不计入当前汇总。
- 必须先通过既定的两表完整性、唯一 UUID、非负整数/数值合法性检查才能保存；真实 0 可以计入，漏行、未知或无效值不能默认为 0 来凑总数。若游戏界面显示的「击杀」与站内「击败合计」有差异，以**本网站定义的击败合计**作为当前站内总击杀，避免混称游戏官方榜单数值。
- **实现边界**：总击杀的唯一可信来源是该场有效个人战绩；实现可在查询时计算或做一致性保证的缓存，但不得再建立可独立编辑、可能与个人明细漂移的总击杀真值。赛事详情须清楚注明「总击杀（个人击败合计）」。具体版本表、审计与事务结构开发时设计，不表示已实施。

### 已闭环的业务规则（不再重复提问）

1. **已确认：严格双表校验**：两表同场的玩家 UUID 集合必须完全一致，否则阻止保存；修正至一致后才能提交。
2. **已确认：新人与历史身份**：新参赛者可在赛事核对时人工新建档案；已建档历史玩家沿用原 UUID。赛事导入不自动改变入会状态。
3. **已确认：保存后单条编辑**：在赛事详情直接修改某个玩家战绩或身份，按严格双表校验保存新版并保留历史审计；不必整场重新导入。
4. **个人资料仅两个可点击统计值**：「参加几场」→ 查看本人参加的各场比赛与本人该场两类战绩；「缺席几场」→ 查看确认在会期间未参赛的场次（无个人战绩）。入会前、退会后和资格状态不明不计缺席；不增加跨场累计排行榜或均值仪表盘。

### 6.1 V1 页面和操作路径（工程建议）

2. 创建：选择俱乐部上下文和比赛日期、手填总积分、粘贴完整 JSON → 结构校验 → 双表逐玩家身份核对/数值更正 → 最终预览 → 一次确认提交。不能因粘贴 JSON 而自动修改每日名册、退会状态或导入 AI 服务。比赛日期或俱乐部和场次类型与已有**有效**记录冲突，提示查看/修正，不覆盖。

4. 玩家资料：仅增加「参加 N 场」「缺席 M 场」两个可点击统计。参加明细可查看本人每场的完整两类战绩；缺席明细只给该场日期/信息，不伪造本人 0 战绩。全部统计以**当前俱乐部**有效赛事、最新版本和保守的成员在会证据计算；不做另一个跨场综合排行榜。

### 6.2 站外 AI JSON 输入样例（**V1 固定工程契约，尚待开发测试**）

**用户已授权由方案设计者自行确定 JSON 字段，不必就字段名另行选择；只需保证可准确录入。** 本节现将字段名、类型与数组结构定为 V1 工程契约，由后续实施的 Prompt、网站导入解析器、Worker/DB 入库校验及测试共同遵循；**目前没有实现或验证真实网站能导入，不能误写为已上线**。JSON 是同一场比赛、同一俱乐部的两组完整数组；示例内容为虚构值。日期、俱乐部 UUID 和总积分来自网站表单/当前俱乐部上下文，**不相信 JSON 自己决定俱乐部身份**。契约如下：

```json
{
  "schema_version": 1,
  "event_type": "four_way_league",
  "output": [
    {
      "player_name": "示例玩家甲",
      "club_name": "示例公会",
      "kills": 9,
      "assists": 26,
      "dispersals": 0,
      "awakens": 0
    }
  ],
  "strategy": [
    {
      "player_name": "示例玩家甲",
      "club_name": "示例公会",
      "player_damage": 501000,
      "damage_taken": 199000,
      "healing": 0,
      "guardian_damage": 4527000,
      "purification": 0
    }
  ]
}
```

- 对应字段：「输出」= 玩家名字/俱乐部/击败/助攻/消散/唤醒；「战略」= 玩家名字/俱乐部/对玩家伤害/承受伤害/治疗/对守卫伤害/净化。两表各独立留存截图昵称和原始内容，**不可按行序配对**。
- AI 优先输出**完整非负整数**，例如 `50.1万 → 501000`、`452.7万 → 4527000`；若输入原文仍有「万」/无法辨识的字符，网页可在人工预览提供受控的换算和纠错，但最终入库必须是非负安全整数。缺失/不清楚填 `null` 并阻止最终保存，**不自动补 0**。
- 检查 JSON 结构、字段全齐、数组长度至少 1、可接受大小上限、昵称和俱乐部字符串、数值及当前选择俱乐部一致性。同表重复玩家、两表 UUID 集合不相等、冲突 ID、人工核对不完整，均阻止确认；重复的悬浮固定行不能被误认为另一个玩家。不能将虚构示例值写成默认值。
- 正确匹配按现有玩家 UUID 与经人工确认的别名；相似名字只作候选。原始 JSON 只供有直接授权的俱乐部成员按现有安全模型访问，联盟会长可看整理后战绩但**不可看原始 JSON**。
- 提示词应要求：仅识别截图中可见真实参赛者；多张滚动截图去重；保留昵称特殊符号；两类数据各一组，不猜玩家/排名/日期，不自动填补缺失字段；仅输出合法 JSON，数值单位统一到整数。验收时同时用「万」、0、null、错名、双表乱序、重复悬浮行和漏行样本测试。

### 6.2.1 豆包/外部视觉 AI 提取 Prompt（**V1 固定工程契约，与 §6.2 同步**）

- 参照用户已经实际使用的每日成员截图 Prompt 编写，继承不猜测昵称、可疑值为 `null`、重复行谨慎去重、合法 JSON、字段固定等原则。
- 截图标签和列名据用户给出的两张四方联赛截图字段核对；保留「单场两数组」已确认的数据分组。**以下英文 JSON 键名和可复制 Prompt 为 V1 工程定稿**，不再向用户询问字段名选择；开发时网站前端、Worker 和测试必须对齐该结构。实际导入测试如发现需要修正，应在文档和实现中一起版本化更改，不可只有 Prompt 或只有代码单方面变更。

```text
请从我上传的《诡秘之主》游戏「四方联赛」结算截图中，提取当前已筛选俱乐部的所有可见参赛玩家数据，并且只输出严格合法的 JSON，不要解释、Markdown、代码围栏或其他文字。

规则：
1. 我可能上传多张滚动截图，图片分别属于「输出」或「战略」标签。全部读取；只提取每张截图实际显示的玩家，不猜测缺失行、不创建不存在的玩家，不读取左侧其他俱乐部的整体排名。
2. 「输出」标签对应字段：玩家名字、俱乐部、击败、助攻、消散、唤醒。映射为 output 数组中每个对象的 player_name、club_name、kills、assists、dispersals、awakens。
3. 「战略」标签对应字段：玩家名字、俱乐部、对玩家伤害、承受伤害、治疗、对守卫伤害、净化。映射为 strategy 数组中每个对象的 player_name、club_name、player_damage、damage_taken、healing、guardian_damage、purification。
4. 优先准确识别昵称中的汉字、繁简、英文、数字及有意义的特殊字符；可忽略明确只是装饰的标点（如「、」「丶」「·」），但不要擅自替换形近字或繁简转换，不要根据另一张表推测昵称。完整昵称认不清时，player_name 填 null。club_name 尽量保留该行显示的俱乐部原文，认不清填 null。
5. 多张截图可能因滚动而重叠，底部也可能有高亮固定的个人行。只有确定同一标签内是同一玩家、且所有可读字段一致，才删除重复行；不能确认是否重复或数据存在冲突时保留不同原始行，交给网站人工核对，不擅自挑一个覆盖另一个。
6. 所有数值都必须输出非负整数或 null。去掉千位分隔符；将显示单位「万」换算为整数，例如 50.1万 → 501000、452.7万 → 4527000；如显示「亿」则乘 100000000。换算只表示截图显示的精度，不凭空补出更多真实末位数字。截图明确为 0 时填 0；看不清、被遮挡或无法确认时填 null，绝不猜测或用 0 代替缺失。
7. 只输出一个 JSON 对象，顶层必须且只能有四个字段：schema_version、event_type、output、strategy。schema_version 固定为数字 1，event_type 固定为字符串 "four_way_league"。output、strategy 必须是数组。每个 output 元素必须且只能有第 2 条所列的六个字段；每个 strategy 元素必须且只能有第 3 条所列的七个字段。字段一个也不能少，也不得新增。
8. player_name、club_name 类型只能是字符串或 null；其他统计字段类型只能是整数或 null。两个标签的行顺序、人数可能不同，必须各自独立提取，不通过排名/行号合并，不为了让两数组人数相同而补玩家、改名或补零。缺少某一标签的截图时，对应数组输出 []，不要虚构。
9. 不要输出比赛日期、玩家 UUID、俱乐部 UUID、总积分、总击杀、参赛总人数、是否完整名单等字段；这些由网站决定或计算。只输出图片中能确认的原始玩家数据，最终由网站进行身份核对。
10. 输出前自检 JSON 语法、字段名、类型和去重规则；最终回复只包含 JSON 本身。
```

- 网站仍应严格进行两数组 UUID 覆盖一致性检查，`null` 必须在预览阶段核对纠正；Prompt 不能证明所有滚动截图已拍全。固定悬浮行只能在「确定重复且数据一致」时去重。
- V1 固定 `schema_version: 1`、`event_type: "four_way_league"`、`output: []` 和 `strategy: []` 四个顶层字段，行保留名字与俱乐部文本，且不混入日期与总积分等站内元数据。网站校验应拒绝缺少任一数组的最终保存（即使 AI 可以在少了截图时输出空数组），同时允许用户在导入预览阶段人工纠错后再确认。

**交付判定（本节仅设计，不等于真实录入已通过）**：Claude / Codex 必须用本 V1 Prompt 生成/手工模拟的正确 JSON 执行完整的前端解析、身份核对、预览、事务性保存、再次读取回显；同时测试空数组、名字 `null`、重复悬浮行、跨表乱序、`50.1万` 换算、坏数值、错误俱乐部、重复 UUID。只有端到端测试通过才可称「录入没问题」。V1 定稿只代表**不用再向用户追问字段名**，不代表已运行通过。

### 6.3 权限实现建议（**并非新用户决定**）

- 仅新增三项赛事业务权限 + **平台管理员专用于赛事权限管理**的授权入口；该入口只能管理俱乐部内 owner/admin 的三项赛事权限，需现有平台管理 TOTP/AAL2，不得授予通用 `platform.permissions.manage`。
- **技术优先级建议**：系统安全/不可委托 → 超管职位上限 → 超管个人强制 → 平台管理员的**个人赛事设置** → 平台管理员的**俱乐部职位赛事默认设置** → 公会长对管理员的个人/默认设置 → 原有默认。超管强制允许只能在未受系统安全/职位上限阻止时生效；平台个人允许能覆盖同层平台职位禁止（用户已确认）。未设置表示「跟随下层」，建议使用允许/禁止/跟随三态，撤销时回退到下一层**当前**配置。必须在已有唯一 `club_private.can()` / `permission_layer()` 授权链及 Worker/DB 一致落实，不得前端自算替代服务端结果。
- 平台赛事权限**管理授权**与赛事实际业务**读/写授权**严格分开；平台管理员不因能改权限就自动能看俱乐部赛事，不能通过自身为目标的权限设置给自己提权。角色更改、撤职重任命时沿用现有例外保留的 RBAC 语义，但始终按当下有效职务、俱乐部及更高层限制重新算权限；应明确显示生效来源。
- 新增读权限需兼容现有联盟只读的 `club` + `alliance`、`read_only` 范围；「导入」「修改」仍是写权限，联盟会长的只读身份不可通过。没有有效「查看」时，即便写项为允许，所有赛事查询/写接口仍拒绝。
- **以上为待审核实施建议**。尤其平台管理员能否个人授权超出职位默认、是否禁止对自己操作、超管的强制允许优先级，虽然符合已确认的高层约束，但需要最终审查安全测试和现有 SQL 兼容性后才能视为工程签核。

### 6.4 数据一致性与验收（默认应做到，不是额外业务新功能）

- 至多一场有效赛事匹配 `club_id + event_type + date`；作废解除有效唯一占位，恢复必须重新检查，无并发重复。日期修正保留原 event UUID，不产生新参赛场次。
- 任意成功写入均为事务性新版：版本号、旧/新值、操作人、时间、来源；错误、取消或并发冲突不产生半套赛事或孤立新玩家。后端再验双表 UUID 集合、非负完整数值及权限。旧版本只用于审计、不进入统计。
- 总击杀唯一计算口径 `sum(有效场次每个参赛玩家最新输出.kills)`；总积分可改，击杀合计不可独立改。玩家参加场次按当前俱乐部有效赛事实有记录计数；缺席只按可确认在会日期、且无该场记录计数；未在会、不确定与已作废比赛不计。
- 用真实 API/数据库权限测试：不同俱乐部隔离、联盟会长只读且拿不到原始 JSON、三项权限依赖、平台个人例外、超管禁止、MFA、撤职重任命、并发冲突。浏览器测试覆盖导入→核对→修正→作废/恢复→个人资料两个入口及旧 `date` 链接回归。
- 保留 V1 最小系统：不新增站内视觉识别 AI、不引入收费基础设施、不改每日成员 JSON/缺席判定流程、不把前端的排序当成数据库排序/业务排名。

### 6.5 审核收尾后的工程边界（无需再次提问已确认规则）

1. **历史资格与暂离**：只在有证据确认赛事当天在会且未参赛时算缺席；暂离、待确认、资料断档、同日入退会先后不明均不计缺席。复用历史状态，不要求每场另拍完整成员名单；必须用测试核对时间线。
2. **身份冲突的人工修复（已确认，非待办）**：先阻止 A→B 直接改绑到已有 B 战绩；管理员核实后，可在赛事详情明确移除确实误录入的一整条「输出 + 战略」记录，保留版本/审计，再单独完成正确改绑。若两人都真实参赛，则修正身份而不是删除真实行；不自动合并或覆盖。
3. **平台赛事管理安全定案**：允许/禁止/跟随三态；平台个人例外覆盖同层职位值，撤销后跟随下一层当前设置；超管上限和强制设置仍优先。平台管理员不得对自己提权，不得获得通用平台权限管理能力；Worker 与 SQL 必须一致。
