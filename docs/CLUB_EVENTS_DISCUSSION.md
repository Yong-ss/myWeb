# Club 活动数据录入 — 四方联赛需求讨论

> 状态：讨论中，尚未批准开发。重置日期：2026-11-04。
> 本文件是与用户持续讨论的需求草案，区分「已确认」「截图可见」「待确认」；不得把建议视为最终决定。
> 本轮只更新这份文档，不修改应用代码、数据库、权限或部署。

## 1. 当前目标（已确认）

- **首个开发活动改为「四方联赛」**；不再以高原竞逐作为首个开发目标。
- 之前讨论的高原竞逐多俱乐部混合势力、身份过滤等专项设计**全部取消出本文件**；不能照搬成四方联赛规则。
- Club 以后可能继续加入其他活动类型，但现在逐个做，先谈清楚四方联赛。
- 用户希望像现有「每日成员数据导入」那样，先用站外视觉 AI 提取截图 JSON，再由 myWeb 处理；**是否以及如何用于四方联赛仍待细化**，不提前锁定完整流程。
- 此阶段只记录需求，讨论完再交由 VS Code / Codex 开发。

## 2. 用户提供的四方联赛截图（直接观察，不代替游戏规则确认）

两张截图顶部均为「势力排行」「数据统计」，右上角筛选值为 **「千秋｜君辞赋」**；左侧显示四个排名条目：
1. 千秋｜君辞赋（图中积分 3000、击杀 131）
2. 夜尽天明（积分 167、击杀 29）
3. 圣维耶芙拉（积分 0、击杀 7）
4. 春风十里（积分 0、击杀 7）

这里仅记录截图所见，**还未确认四方联赛每支队伍是否严格对应一个俱乐部**、每场是否四队同时参与，以及排名中的「击杀」是否可由个人击败累加获得。

### 截图一：「输出」标签

表头为：**玩家名字、俱乐部、击败、助攻、消散、唤醒**。

- 截图展示多名玩家及所属俱乐部列，当前可见行的俱乐部显示为「千秋｜君辞赋」。
- 例：玩家「北忧」的数据显示击败 9、助攻 26、消散 0、唤醒 0。
- 当前截图为滚动列表的一部分，不能凭此断定全部玩家都已拍到。
- 底部另有高亮固定的「北忧」行，看起来与列表内「北忧」的数值相同；**解析时应避免把固定展示行当作第二个人，但重复行判断规则仍待核实**。

### 截图二：「战略」标签

表头为：**玩家名字、俱乐部、对玩家伤害、承受伤害、治疗、对守卫伤害、净化**。

- 例：「北忧」的数据显示对玩家伤害 50.1万、承受伤害 19.9万、治疗 0、对守卫伤害 452.7万、净化 0。
- 此截图中的「输出」和「战略」分类及其字段，以**四方联赛截图的实际标签**为准，不沿用此前其他活动截图的字段归类。
- 「万」等数值单位需要在未来 JSON 契约中统一处理；缺失或无法识别不能擅自填 0。
- 两页排序不同；**不能按排行榜行号合并两页数据**。

### 目前可合理讨论但未批准的做法

- 如果确认截图里的「俱乐部」列可靠且包含所属俱乐部，就可以优先按照该列过滤自己俱乐部的玩家，这会比高原竞逐混合势力容易得多；仍要处理名称不一致和录入时玩家转会的情况。
- 两份数据应在确认是同一场活动、同一位玩家后合并；匹配优先考虑昵称与现有玩家 UUID / 已确认别名，发生冲突时人工核对。
- 不改变现有每日成员 JSON 格式；另定四方联赛的 JSON schema 和专用站外 AI Prompt。

## 3. 需要向用户确认的下一件事

**四方联赛截图中的「俱乐部」一列是否能准确区分所有参赛者的实际俱乐部？** 例如右上角选中「千秋｜君辞赋」后，列表是否已经只显示这个俱乐部的玩家，还是会出现其他俱乐部的玩家？

这个答案会直接决定是否还需要从大量陌生玩家中筛选本俱乐部成员。

其余待讨论事项（暂不决定）：一场活动如何标识及补录；是否可以同时上传多张滚动截图；同场两类统计如何完整性校验；谁能导入/编辑；历史排名与报表；重复导入和版本处理；当前/历史成员的关联规则。

## 4. 现有系统边界

- 既有 Club 每日名单导入、玩家 UUID/别名、Club RBAC、Worker/RLS、审计和测试机制应复用，不破坏原功能。
- 现有 `/activity` 是**操作审计日志**，不能直接视为游戏活动页面。
- 暂无理由增加 Redis、消息队列、微服务或付费 AI API。
- **只讨论并更新本文件**；尚未授权数据库迁移、生产数据写入、改代码或部署。
