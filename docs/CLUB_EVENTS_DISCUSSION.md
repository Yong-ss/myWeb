# Club 四方联赛 — 需求讨论草案

> 状态：**需求探索中，尚未批准开发**。重置日期：2026-11-04。
> 本文供后续与 Codex / Claude 协作使用。区分「已确认」「建议」「待确认」；不要把尚未确认的玩法或数据结构当作既定要求。

## 1. 当前目标（已确认）

- Club 未来可能管理多种游戏活动，但**当前第一个要讨论并开发的是「四方联赛」**。
- 原先计划优先开发的「高原竞逐」**暂缓**，因为其一个势力内混有多个俱乐部的成员，识别并筛选本俱乐部人员的流程较复杂。
- 此次直接重置需求草案；**不把高原竞逐的四势力结构、混合俱乐部名单、输出/战略统计字段和截图识别规则直接移植到四方联赛**。
- 先了解四方联赛的实际玩法、结算界面和需要记录的数据，再确定活动流程、JSON 契约、权限、数据模型及 UI。

## 2. 现有 Club 能复用的技术基础（已从仓库确认的方向，非新需求）

- 现有玩家有内部 UUID、正式昵称、已确认别名和历史身份记录；设计时优先复用，避免重新建立玩家身份系统。
- 已有「外部 AI 从游戏截图提取 JSON → 网站校验、核对、确认保存」的成员资料导入经验，但**四方联赛是否使用截图、JSON 或手工录入仍待确认**。
- 俱乐部成员因为 GVG 竞技会较频繁加入和退出，昵称相对稳定、偶尔改名；游戏中虽有玩家唯一 ID，但不能假设任何四方联赛截图会显示它。
- 新功能应符合现有 Club 的俱乐部数据隔离、RBAC、Worker 服务端授权、Supabase RLS、审计与测试约定。
- 现有 `/activity` 是业务**操作日志**，不是游戏活动记录；未来的游戏活动路由与命名须区分。

## 3. 四方联赛需要从零确认的游戏与录入规则

1. 四方联赛的参与方式是什么？每队/每方是独立俱乐部，还是可能混合其他俱乐部？
2. 游戏结算会展示什么数据？玩家个人统计、俱乐部/队伍统计、排行榜还是其他形式？
3. 需要记录什么：每场比赛结果、个人表现、团队成绩、积分、排名、胜负或其他字段？
4. 是否有一场多局、同日多场、不同阶段等结构？日期、服务器时区、赛季/轮次如何表示？
5. 数据来源是什么：截图、手动输入、外部 AI 生成 JSON，还是组合？
6. 如果使用截图，截图是否包含昵称、游戏 ID、俱乐部归属；是否需要多张截图拼接？
7. 玩家匹配是否必要？历史退会成员、新成员、重名及改名如何处理？
8. 谁可以录入、核对、修改和查看？是否需要重新录入、版本历史与误操作恢复？
9. 第一版最终需要哪些页面及分析统计，哪些以后再做？

## 4. 初步设计原则（建议，尚未确认）

- 尽可能沿用现有架构与 UI，不引入不必要的付费 AI 或新服务。
- 先做可人工核对、可追溯的最小流程，再考虑自动化；任何 AI 识别结果不能默认全部正确。
- 玩家数据使用内部 UUID 关联；昵称只作为候选匹配线索，避免重名与改名造成身份错误。
- 缺少的数据与实际 0 要区分；活动历史不能因为成员后来退出俱乐部而消失。
- 需求明确后才设计数据库 migration、Worker API 和页面；不要提前照搬其他活动字段。
