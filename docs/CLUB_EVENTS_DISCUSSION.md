# Club 活动数据录入 — 需求讨论草案

> 状态：讨论中，**尚未批准开发或迁移**。建立日期：2026-11-04。
> 用途：记录与产品负责人逐步确认的需求，供后续 VS Code / Codex 实现前审阅。
> **本文件为讨论记录，不等于功能已经实现。** 更新时区分「已确认」「建议」「待确认」，不要将建议自动视为决定。

## 1. 产品方向（已确认）

- Club 不止一种游戏活动：目前提到「高原竞逐」「四方联赛」「势力竞争」等。先逐个开发，**第一个只做高原竞逐**；架构上应能扩展不同活动类型及其独有字段。
- 「高原竞逐」一场有 **四个势力**（即此前口头所说四支队伍），每个势力可由多个俱乐部的玩家混合组成。
- 游戏结算展示的是**当前势力的全部玩家**，并不直接按俱乐部筛选；myWeb **只记录当前俱乐部所属玩家的个人数据**，其他俱乐部的数据不应误保存为本俱乐部战绩。
- 需要记录同一场次的两类结算数据：**输出统计**和**战略统计**，并按同一玩家合并。
- 俱乐部为 GVG 竞技频繁招募、替换成员，因此**不能要求每次导入活动之前必须先更新完整的每日成员名单**。
- 玩家昵称总体稳定，偶尔会改名；游戏中存在唯一玩家 ID，但**结算截图没有 ID**，须逐个点开玩家个人资料才看得到，故活动导入不能依赖手动逐人查 ID。
- 继续沿用已熟悉的工作方式：**站外视觉 AI 识别截图 → 输出结构化 JSON → 粘贴/导入 myWeb → 网站匹配并由管理员确认 → 保存**。外部 AI 无需访问俱乐部成员数据库。

## 2. 高原竞逐数据范围（已讨论，具体字段待截图/游戏术语最终核对）

### 战略统计
- 玩家昵称、所属势力、击败、助攻、消散、唤醒、战功。

### 输出统计
- 玩家昵称、所属势力、对玩家伤害、承受伤害、治疗、净化。

### 录入上下文（建议，待确认）
- 俱乐部、活动类型、活动日期/时间、场次标识、所属势力、备注。
- 一场活动可能需要多张截图覆盖同一势力的全部玩家；JSON 可以分别导入两类数据。
- 数字统一转换成数据库数值；例如「27.1万」须准确换算。**看不清/缺少的字段用 null，不得当成 0**。
- 输出/战略统计可能独立排序；**不能按截图行号或排行榜名次合并**。

## 3. 拟议的导入与匹配方案（建议，未冻结）

1. 用户按已有成员导入的方式复制专用 Prompt，给外部 AI 两类结算截图。
2. AI 仅忠实提取截图可见的**当前势力所有玩家**及数值，输出活动专属版本化 JSON。不推断俱乐部归属、游戏 ID、缺失字段或玩家身份；保留来源类型（输出/战略）。
3. myWeb 验证 JSON 结构、数字、重复行、来源类型及批次冲突，先将两类数据按原始昵称/候选昵称进行暂时关联；无法确定的跨图同人关系交给用户核对。
4. **复用现有 Club 的玩家 UUID、正式昵称、已确认别名和身份匹配机制**。优先处理明确且唯一的匹配；相似昵称、冲突、同名和未匹配都要人工确认，**不能凭猜测自动认定**。
5. 匹配范围同时考虑历史玩家，避免退会后旧战绩消失；当前名单不完整时，提供选择历史玩家、新成员或排除为外俱乐部玩家的操作。是否属于**该场活动发生时**的本俱乐部，必要时由管理员明确确认。
6. 预览时只将管理员确认属于本俱乐部的人纳入正式记录；其他势力成员不写入本俱乐部活动战绩。未匹配行要显式可见，不可静默丢失。
7. 两类记录最后归并到**同一个确认后的玩家 UUID + 同一活动场次**，展示缺失、重复、冲突，并允许修正；最终人工确认后提交。
8. 保留足够的昵称与参与身份快照，以便历史记录不被后来改名、离会或再次入会覆盖。游戏 ID 可作为玩家档案可选信息，**不是导入必填项**。

## 4. 与现有系统的边界（已查阅仓库约定）

- 已有 Club 每日名单导入定义在 `docs/CLUB_REQUIREMENTS.md`，JSON v1 包含九项成员资料；**高原竞逐应定义独立的活动 JSON 契约，不改坏旧格式或旧 Prompt**。
- 现有 `/activity` 是**操作审计日志**，不是游戏活动；新功能应避免与其路由和概念冲突（例如新路由 `/events`，仅为建议）。
- 现有 `apps/club/AGENTS.md` 要求功能隔离、权限检查、RLS、专用事务 RPC、审计、测试，后续实现必须遵守。
- 多俱乐部数据隔离；不把某个势力混合玩家全部直接导入当前俱乐部；不能信任客户端自报 club_id 或仅以 UI 过滤作为安全控制。
- 目前**不需要**引入 Redis、微服务、消息队列或站内付费 AI API。

## 5. 必须讨论/决定的问题（待确认）

1. 同一场次如何唯一识别（日期、开始时间、场次编号、同日多场、时区）？如何避免重复导入/覆盖？
2. 两张截图若出现同昵称不同人、玩家改名、只有一张统计表、排名顺序不同，该怎么提示和操作？
3. 当前名单经常变化：导入时如何明确「该玩家在活动当天属于本俱乐部」？是否需要当时参与名单或归属状态快照？
4. 首次未匹配的新玩家：在活动界面建立新玩家档案、待确认身份，还是先临时留在草稿？
5. 导入草稿/预览如何防止刷新、离开导致丢失？原始 JSON 是否保留、保留多久、谁可见？
6. 需要哪些查看、筛选、成员历史、排名或统计？第一版做到什么程度？
7. 活动录入、编辑、删除分别开放给哪些 Club 权限？如何审计与版本化？
8. JSON 的完整字段名称、数值单位、必填/可空规则，以及单批行数与大小上限。
9. 两类截图是否会包含「所属势力」且如何准确确认？是否需要跨多个势力导入同一场？
10. 活动记录应否包含已退会玩家的历史战绩；统计中如何区分当时成员和当前成员？

## 7. 导入预览交互改进（2026-11-04，待最终确认）

- 用户明确指出：一个势力含大量其他俱乐部玩家，不能把**所有未匹配昵称**都当成逐人待确认任务；否则核对工作量过大。
- **当前建议（待用户最终确认）：** 以本俱乐部已知玩家为主的自动匹配与预选；其他未匹配玩家默认折叠/不选中，**不要求逐个决定是否属于外俱乐部**。显示未匹配人数即可。
- 提供「搜索全部识别玩家 / 添加漏录新成员」入口，让管理员从完整临时识别结果里快速选出真实的本俱乐部新人；也支持手动关联历史玩家或新建档案。
- 保存前明确显示已选本俱乐部成员数量、疑似匹配/重名冲突，以及未选中的其他识别玩家数量。未选中的数据不进入正式本俱乐部战绩；在本次导入草稿/预览内保留以便找回，但临时数据保留策略尚待决定。
- 不应将匹配不到的昵称自动判定为外俱乐部，亦不得把疑似昵称直接自动匹配；自动预选仅在已唯一且可信的身份映射成立时进行，管理员可撤销和修正。
- 必须进一步讨论如何避免**过时成员名单导致已退会玩家自动入选**，以及如何便利地批量确认实际参与者；切勿将「自动匹配」等同于「活动当时属于本俱乐部」。
