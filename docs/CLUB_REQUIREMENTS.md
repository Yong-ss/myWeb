## 1. 产品目标与范围

- SquirrelAPI 的第一个独立应用，计划地址：`club.squirrelapi.org`。
- 《诡秘之主》游戏俱乐部每日数据管理：管理员用外部 AI 从游戏截图提取 JSON，网站负责验证、导入、保存历史记录与分析变化。
- 第一版只服务自己的俱乐部；数据结构从第一天支持将来多个俱乐部，互相隔离。
- 普通游戏成员仅作为数据记录对象，暂时无需账号，也不公开俱乐部成员数据。
- 尽量复用现有私有 Monorepo、Cloudflare Workers 免费方案、现有 Supabase 项目；除已有域名费用外，新增预算 RM0。
- 第一版不接入付费 AI API，也不直接在站内识别截图。

## 2. 角色与账号

- **Super Admin（平台管理员）**：创建俱乐部、任命或更换公会长、管理整个平台。
- **Owner（公会长）**：负责本俱乐部，邀请、指定和撤销本俱乐部管理员；也能管理普通玩家、导入和分析数据。
- **Admin（俱乐部管理员）**：管理本俱乐部普通游戏成员、导入和纠正数据、查看分析；**不能**任命或撤销其他管理员。
- **普通游戏成员**：不是登录角色，不需要创建用户账号。
- 账号采用邀请制：平台管理员创建俱乐部并邀请公会长，公会长邀请管理员。受邀者自行激活账号/设定密码；不开放任意创建俱乐部。
- 一个账号未来可在不同俱乐部担任不同角色。权限依据「用户 + 俱乐部」关联判定，不是账号全局单一角色。
- 现有主站仅限站长的登录已上线；不能因为开发 Club 而破坏主站登录。跨子域登录及具体邀请发送方式留到技术设计时确认。

## 3. JSON 数据契约 v1（拟在开发前冻结）

统一采用英文键名；中文内容使用字符串。JSON 顶层固定：
- `schema_version`：整数，固定 `1`
- `snapshot_date`：AI 输出 `null`，由导入页面填写实际截图日期（`YYYY-MM-DD`），可补录
- `is_complete_roster`：AI 输出 `false`，由管理员在网站确认是否包含完整成员名单
- `members`：玩家对象数组

每个玩家对象必须包含以下**九个字段**，不增加 `online_status`：
- `name`：昵称，字符串或 `null`
- `position`：职位，字符串或 `null`
- `level`：等级，整数或 `null`
- `pathway`：途径，字符串或 `null`
- `extraordinary_score`：非凡评分，整数或 `null`
- `prosperity`：繁荣度，整数或 `null`
- `weekly_activity`：周活跃，整数或 `null`
- `group`：分组，字符串或 `null`
- `join_days`：游戏显示的入会天数，整数或 `null`；不要让 AI 推断具体日期

示例（演示数据，非真实玩家）：

```json
{
  "schema_version": 1,
  "snapshot_date": null,
  "is_complete_roster": false,
  "members": [
    {
      "name": "玩家甲",
      "position": "正式会员",
      "level": 70,
      "pathway": "占卜家",
      "extraordinary_score": 168898,
      "prosperity": 16189,
      "weekly_activity": 45,
      "group": "一组",
      "join_days": 64
    }
  ]
}
```

网站需校验字段、数据类型、JSON 语法、同批次重复/冲突信息；不能以不同 AI 的字段顺序来判断格式是否合法。错误数据在确认导入前可修改。AI 输出的原始 JSON 应可追溯；不把不确定识别结果直接写成已确认的成员身份。

## 4. 复制给外部 AI 的统一 Prompt（复制按钮使用完整正文）

> 请从我上传的《诡秘之主》游戏俱乐部成员截图中提取所有可见的玩家资料，并且**只输出严格合法的 JSON**，不要解释、Markdown 或代码围栏。
>
> 规则：
> 1. 只读取截图实际显示的数据，不猜测、不补全、不生成不存在的玩家；多张截图都要读取。
> 2. 玩家昵称尽量准确识别汉字、英文和数字；可忽略装饰性标点（如「、」「丶」「·」），但不要自行替换形近汉字，也不要擅自将繁体转成简体。看不清的完整昵称用 `null`。职位、途径、分组保留截图文本。特别注意玩家昵称的识别准确性。对于复杂汉字、形近字和小字体，请仔细观察，必要时放大图像中的昵称区域进行辨认。不要凭常见字词猜测昵称，无法确认时填写 `null`。
> 3. 只有能确定是同一玩家且各项数据一致，才对多张截图的重复记录去重；不能确认或数据冲突时保留待人工检查，不猜测合并。
> 4. 数值字段必须为整数，去除千位分隔符；无法确认填 `null`。入会时间「64天」输出 `"join_days": 64`，不推算日期。
> 5. 不计算数据变化，也不判断玩家是否离会。
> 6. 顶层必须包含 `"schema_version": 1`、`"snapshot_date": null`、`"is_complete_roster": false`、`"members": []`。每名玩家严格包含 `name`、`position`、`level`、`pathway`、`extraordinary_score`、`prosperity`、`weekly_activity`、`group`、`join_days` 九个字段。
> 7. `name`、`position`、`pathway`、`group` 的类型为字符串或 `null`；`level`、`extraordinary_score`、`prosperity`、`weekly_activity`、`join_days` 的类型为整数或 `null`。所有对象字段必须齐全；不要新增字段。
> 8. `snapshot_date` 与 `is_complete_roster` 由网站导入时决定，AI 必须分别输出 `null` 和 `false`。

注：Prompt 的输出类型不等于识别准确率保证。跨 AI 测试已报告三份 79 人 JSON 格式一致，但九名玩家昵称存在异字。网站必须支持人工修正；原始输入应可追溯。更新 Prompt 和网站校验规则时要同步版本。

## 5. 导入页面 UX（第一版范围）

- 「复制 AI 识别 Prompt」按钮：一次复制第 4 节完整 Prompt，给出复制成功提示。
- 在按钮旁显示「推荐使用豆包」，提供官网链接 `https://www.doubao.com/chat/`；同时明确其他支持图片的 AI 也可以使用。
- 简短流程：复制 Prompt → 打开豆包/其他 AI 并上传截图 → 复制生成的 JSON → 回网站粘贴 JSON 或上传 .json → 预览修正 → 确认导入。
- 导入前显示成员列表、字段异常、重复/冲突与可能身份匹配情况；允许人工编辑和确认。
- 导入时设置 `snapshot_date` 并明确勾选「已提供完整成员名单」；默认**未确认完整**，不能据此自动判断离会。
- 避免同俱乐部同日期同一批数据无意重复导入；如补录或修正已有记录，明确提醒并保留可追溯变更，不悄悄覆盖。
- AI 不需要知道俱乐部数据库 ID；实际俱乐部由已登录用户及当前选定俱乐部决定。

## 6. 玩家身份、历史数据与分析

- 每个俱乐部的玩家具有稳定的内部 ID，与每日快照记录关联；昵称不是主键。
- 将 AI 提取的昵称和适当去除装饰符号的「匹配昵称」分开处理。标准化仅作为候选匹配线索，不能自动确认同一人；形近字（如「冷／泠」）尤其需要人工处理。
- 每天保存快照；缺失值为 `null`，不能错误当成 0。
- 网站根据相邻可比较快照计算：非凡评分绝对变化与百分比、繁荣度变化、周活跃的变化；周活跃可能周期重置，不能直接解读为累计增长。
- 已确认完整名单中未出现的既有成员，显示为暂时「离会」，排序到列表末尾并以红色删除线表示；以后重新出现自动恢复，并保留离会和重返的历史。**不完整名单不得触发离会判断**。
- 第一版提供当前成员列表、搜索/排序、历史日期查询、个人趋势、排名和基础变动统计。
- 入会日期若需显示，只能根据 `snapshot_date - join_days` 估算并标注为估算值。

## C 第一批：成员名单与日期查询 — 2026-10-27

## C：成员状态与个人历史 — 2026-10-28

- 首页、登录页已迁移至现有共享组件与同一主题；认证提交、会话、权限保持原行为。
- 名单增加在会／本次未识别／暂时离会及数据日期。人数摘要是该日实际保存人数，历史缺席记录不混入当日人数；缺席记录展示最后观察值并标明日期，不把旧数据冒充当日数据。
