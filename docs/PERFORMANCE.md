# 数据读取与性能规范

## P4 角色管理（本地）— 2026-11-01

角色上下文通过一个 RPC 读取目标账户角色及俱乐部列表，沿用 P3 小规模全俱乐部选择契约（达到数百俱乐部后需要分页）。角色变更一个事务／RPC，按俱乐部串行化，不逐角色远程写入，不建立权限缓存；角色版本和私有请求账本用于并发／幂等，写后使用既有失效广播重读。上下文按需打开弹窗才读取；未来管理员上限可用每俱乐部配置调整，本期无配置编辑入口。未声称已完成多俱乐部写入性能基准。

## 平台玩家人数（P3.1，本地）— 2026-10-31

总览仍由一次 `platform_overview` RPC 返回全部俱乐部，数据库内部按俱乐部复用 `club_roster_presence`，不逐玩家／俱乐部发起远程请求、不读取全部原始历史 JSON、不新增缓存。保留名单现有的每俱乐部小于 1,000 历史身份、最多 200 个当日观察的保护上限，超限明确失败，不返回截断统计；本次没有测量生产延迟或证明无限扩容。多俱乐部增长后需根据真实查询计划评估，不能另建一套状态算法。

## 权限切换（P2）— 2026-10-30

同一台机器、同一 80,000 行夹具（`CLUB_PERFORMANCE=1`），P1（origin/main）与 P2 交替各跑 3 次：名单 warm 中位数 114→123 ms，分页历史 111–138→109–154 ms，完整历史 275–310→315–394 ms（其中 Auth 调用本身波动 110–169 ms），RLS 查询计划 0.2→2.3 ms。单次 RLS 读取（80 行，500 次平均）0.02→0.3 ms，来自业务 RLS 改用 `readable_clubs()`。`super_admin_active()` 最初对 aal1 请求也查 Auth 会话表，使 RLS 计划达到 5–10 ms、单次读取 0.8 ms；改为 aal1 时直接返回后恢复到上面的数字。结论：没有明显退化，暂不进一步优化；若成员或俱乐部数量增长到 RLS 计划超过约 20 ms，再考虑缓存 `readable_clubs()` 结果。

## 评分历史 — 2026-10-30

`GET /api/members?trend=1&before=<日期>` 复用 Worker 的会话、实时 membership 和用户 JWT/RLS；只读查询服务器指定 Club 的 current、未删除快照。每页 30 天加 1 条游标探测，每个快照最多 201 个当日评分以检测 200 人业务上限；一个嵌套 REST 请求，不逐日／逐成员查询。返回已知总分、缺失数、完整性及版本身份；点击／聚焦日期才复用名单接口读取所需两天的详细资料。分页按日期向前，页面明确展示已加载范围，不声称包含全部历史。详情与曲线版本不一致时要求刷新。

2026-10-28 缺席核对增量：支持新 schema 时，名单由「日期／版本选择 + club_roster_presence」两个数据库 REST 请求完成（此前四次读取链路保留为缺少 RPC 时的兼容回退）。同一个有界 invoker RPC 读取最近观察、完整名单及明确退会，不为每位玩家调用接口；单元测试保护两次请求预算。导入对比复用同一读取，准备时与身份／同日版本并行，避免核对后再等待远程对比。历史分页补齐页边界前的明确退会。没有新的权限缓存或公共数据缓存；未声称已测得线上延迟改善。

## 范围与基线

保留静态 Next.js、Worker、Supabase 和现有 RLS。Club 的账户、名称、名单、个人档案、总览、导入上下文全部检查；主站仅账户认证，无历史业务查询，继续独立，不为两个应用建立共享权限缓存。没有添加依赖或付费设施。

用户提供的开发环境截图：名单接口约 1.57 秒，报告 TTFB 约 1.54 秒，名称约 895ms；这不是受控基准，不能据此计算优化百分比。应用脚本与样式不是主要等待来源。总览之前先账户、再名单、再前一天；个人历史之前每 200 天一次远程请求，最多 2,000 天。名称与各页面独立验证账户／权限。名单四次 REST 查询，其中三阶段串行；精确 count 未使用但每次请求都要求计算。

## 已采用的规则

- Worker `timing.ts` 在请求本地累计 Auth、membership、database 的请求数及等待时间，输出 `Server-Timing`；并行耗时累计值可能超过总耗时。数据库项含 REST／网络，不冒充 PostgreSQL 执行时间。不输出 SQL、Token、账户或业务资料。
- 名单日期确定后，名单行、历史最近观察、最后完整名单并行；四次 REST 不增加，不逐人请求。去掉无消费方的 `Prefer: count=exact`。
- 新个人历史使用 `paged=1`：单次 invoker RPC、每页最多 100 天，以严格 `snapshot_date < before` 游标向前；俱乐部每日当前版本唯一，所以日期是稳定排序键。页边界查询此前最近观察及完整名单，继续正确计算暂离／重返及评分差值，不能把分页首行当首次加入。旧接口兼容保留，其 2,000 天上限不适用于新分页。
- SQL 采用 SECURITY INVOKER、空 search_path、现有 JWT 和 RLS；明确撤销 PUBLIC／anon 执行权限。新索引只针对最近完整名单，已有当前日期唯一索引及玩家复合索引继续复用。RPC 对象显式限制天数，不建立包含整个俱乐部历史的巨大 JSON。
- JWT 本地验签并不能刷新 membership；本轮保留远程 Auth、实时 membership、Refresh 和服务端固定 CLUB_ID，优先撤销时效。没有缓存权限或放宽 RLS。未来多俱乐部选择必须由服务端核实所选俱乐部，再加入缓存 scope，不能只信客户端 club_id。

## 前端统一入口

所有 Club 请求用 `lib/data-access.ts` 的 `clubFetch`，不要另装 SWR／TanStack 或各写一套缓存。

- 私人结果只在内存，最多 40 个 URL、TTL 30 秒；只缓存名单／个人历史与名称。账户与导入预览永不复用旧结果。
- 由服务端认证后返回 `X-Club-Scope=user:club`。每次复用都先实时 GET account，scope 不符就清除；401/403、失败校验不返回缓存。不承诺完全无网络的即时显示，安全门仍需两次远程检查。
- 同 URL 在途请求合并，消费者取消不会取消其他消费者。调用者继续用 AbortController 屏蔽卸载后的 UI 更新。读取超过 5 秒的有效缓存后后台刷新；消费者 `useDataRefresh` 订阅刷新／焦点。超出 TTL 等真实结果。
- 登录、登出和所有写请求开始／结束都清理；BroadcastChannel 通知其他标签页。代际编号阻止旧请求在登出／导入后回填。不得缓存到 localStorage、公共 CDN 或共享 Worker 全局 Map。
- 精确 URL 为键（查询参数顺序要保持统一）；日期、版本、player、分页游标全部在 URL。缓存错误不覆盖成功结果。名称保存仍更新品牌订阅。
- 预取不是默认逐行触发：目前不对 79 个玩家批量预取，以免免费额度和数据库压力增加；未来仅在测量证明收益时对明确意图的链接做去重预取。

## 新 API 与增长

先画依赖链；独立读取并行，有共享快照一致性或减少多轮往返收益时才用小 RPC。查询显式列与租户过滤，RLS 再兜底。列表 limit+1 判断下一页，游标包含唯一排序键，不采用不断增长的 OFFSET。任何上限要明确报错，禁止静默截断。嵌入 JOIN 不是浏览器 N+1，但仍要检查数据库执行计划。

名单当前保留 200 人／1,000 个历史身份保护上限；并行后仍需一次读取历史身份最近观察，身份积累很多时会变贵。不能声称已无限扩容：接近上限时再引入可按日期验证的成员状态摘要或分段列表，先保留旧快照可重建；不现在引入 Redis、分片、读副本。新分页历史前端随点击累积，极大档案后续再加窗口化，当前首屏只渲染 100 天。每页依据请求时的当前修订计算，历史修正期间不是跨请求数据库快照；写后缓存失效，重新打开以获取一致新版本。

## 测量与测试

`pnpm test:integration` 保留日常正确性测试；大规模测试手动设置 `CLUB_PERFORMANCE=1`，再执行 `pnpm test:integration -- performance.spec.mjs`。它只用已有专用可销毁 Supabase，生成 80,000 行，读取查询计划，输出 `.test-artifacts/performance.json`。不向正式库插入数据，不把容易波动的毫秒数作为 CI 门槛。普通 CI 检查缓存隔离／失效、固定查询次数及并行度，已有 affected 策略仍适用。

线上诊断：登录 Club，在 DevTools Console 粘贴 `scripts/club-read-diagnostics.js` 内容，再执行 `clubReadDiagnostics(5)`；只允许 Club 正式／本地 origin，只 GET，输出耗时、字节数、状态与安全计时头，不输出业务内容或凭据。在个人档案执行会额外测分页历史。前后在同一设备／网络／日期重复，并分别记录首次观察、后续访问和页面返回；首次不等于真正冷库。至少 20 个样本才给 P95，5 个样本仅作定位。诊断不会在普通页面后台自动跑。

本地数据库 EXPLAIN 只证明本地计划；正式 Cloudflare→Supabase 网络、区域、冷启动需要上线计时头后收集。正式索引／RPC 尚未应用，不能声称已改善线上 TTFB。生产迁移需先按现有人工迁移／schema 版本门禁流程批准；部署不能跳过该门禁。

参考：[Supabase JWT](https://supabase.com/docs/guides/auth/jwts)、[数据库函数与 invoker](https://supabase.com/docs/guides/database/functions)。

## 2026-10-28 本机结果

合成 1,000 天 × 80 玩家 = 80,000 行，真实本地 Auth／PostgREST／Worker；无模拟业务 API。名单基准固定旧提交 c56d6d3，与新实现用相同输入及同一数据库，执行顺序先旧后新，因此不能当成严格冷／热对照。

| 测量 | 旧实现 | 新实现 |
|---|---:|---:|
| 名单处理器首个观察样本（不含 Auth） | 95.3ms | 78.8ms |
| 名单后五次中位数 | 85.2ms | 79.3ms |
| 名单 REST 次数／输出字节 | 4／34,281 | 4／34,281 |
| 名单 DB 请求依赖阶段 | 3 | 2 |
| 个人历史完整 HTTP 单个样本 | 152.3ms | 114.1ms |
| 个人历史业务 REST 次数 | 7 | 1 |
| 个人历史响应字节 | 432,936 | 45,402 |
| 个人历史 Worker 总计 | 127ms | 57ms |

个人历史新旧结果范围不同（全部历史与首屏 100 天），节省来自按需加载，不能当作相同工作量的 SQL 加速比例。数据库日期页 EXPLAIN 在 authenticated/RLS 下使用 Index Scan，100 行、8 个 shared buffer hit，执行约 0.096ms；这只是该查询，不是整个 RPC 或 TTFB。样本不足，不报告 P95；线上首访、返回页面、历史日期和 Cloudflare 网络尚未测量。缓存单位测试证明命中不再查业务数据，但仍保留实时 Auth／membership 门，不能声称返回页面零延迟。

CI 保留 affected 策略，手动工作流可勾选 performance 运行大数据基准并保留三日报告；普通 CI 不执行该重夹具，也不比较毫秒阈值。本次尚未推送，因此没有新的 GitHub CI 结果。

迁移前本地兼容：仅在分页 RPC 返回 404／PGRST202（函数不存在）时，回退现有 RLS 只读历史查询，再切成 100 条日期页；旧逻辑 2,000 天保护上限仍保留。权限错误、数据库异常不回退。响应 X-Club-Read-Mode=legacy-schema 可供诊断；迁移前不能获得单 RPC 的性能收益。已对正式 REST 做匿名 GET 元数据探测确认函数缺失，未读取业务记录或执行写入。计时处理必须保留只读代理头及 WebSocket 101，不可重建升级响应。


刷新显示规则：同一查询后台更新时保留已有内容，不切换整页 Loading；切换日期／版本仍等待对应结果，防止把旧名单当新日期展示。个人历史重复刷新同一游标须按日期去重。已用延迟响应的 Playwright 验证后台刷新时表格持续可见。
