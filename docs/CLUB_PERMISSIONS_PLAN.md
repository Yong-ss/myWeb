# Club 权限系统 V1：实施计划与进度记录

产品规范 V1（2026-11-02，owner 确认）的落地计划。**本地开发与测试已批准；生产迁移、commit、push、deploy、生产数据均未批准。**
每完成一个阶段，在 §6 记录改动、迁移和验证结果。规则有疑问时以本文 §1–§2 为准；与已有 DECISIONS.md 冲突的条目在 §3 列明取代关系。

## 1. 已确认的产品规则（摘要，不得省略）

- **五种固定职位**，不可自由创建：超级管理员、平台管理员、联盟会长、公会长（owner）、俱乐部管理员（admin）。
- **身份相互独立**：平台、联盟、俱乐部身份各自独立。普通职位或权限设置永远不能授予、修改、撤销超级管理员身份（`platform_super_admins` 只能由迁移或 SQL Editor 改）。
- **单职位**：同一用户在同一俱乐部最多一个生效职位（公会长或管理员）；不同俱乐部可不同。
- **超级管理员**：全部业务与管理权限；需可信 TOTP（aal2 + SQL Editor 确认过的验证器，现有机制）；可设全平台默认权限、职位权限上限、个人权限（强制）、每个俱乐部管理员人数上限（默认 5）；任命/撤销平台管理员、联盟会长；任命/撤销/转让俱乐部职位。
- **平台管理员**：管理俱乐部和用户；任命/撤销/转让公会长；任命/撤销管理员；任命/撤销联盟会长；日常平台业务。**不能**：改任何默认权限、个人权限、权限上限、联盟会长权限；任命/撤销/修改超级管理员；改核心安全配置；关闭/删除/修改审计。**需要 TOTP（aal2），但不需要 SQL Editor 确认验证器。**
- **联盟会长**：只读查看所属联盟旗下俱乐部的成员与业务数据、导入与历史、分析、操作日志；敏感个人信息隐藏；不能修改任何数据、身份、权限。若同时是某俱乐部公会长，只在该俱乐部有管理权。
- **公会长**：管理自己的俱乐部；任命/撤销本俱乐部管理员；调整本俱乐部管理员默认权限与个人权限。**不能**：改自己的权限、改其他俱乐部、突破上限、把任命或权限管理能力授予管理员、改平台/联盟规则。
- **管理员**：只用最终获授权的业务功能；不能改权限、任命、撤销。
- **人数上限**：每俱乐部默认 5 名管理员，只有超级管理员可改；达到上限不能再任命。
- **权限计算顺序**：① 系统安全限制 → ② 超级管理员设的职位上限 → ③ 超级管理员强制的个人权限 → ④ 公会长在允许范围内设的管理员个人权限 → ⑤ 本俱乐部该职位默认权限 → ⑥ 全平台默认权限。个人权限三态：跟随默认 / 单独允许 / 单独禁止。个人允许不能突破上限；明确禁止优先于普通允许。改默认权限后，没有个人例外的人立即跟随；个人例外保留但受最新上限约束。
- **身份撤销**：撤销某职位、移出指定俱乐部（阶段 A）、移出全部俱乐部（阶段 G）、设为无俱乐部身份、重新任命。不删除账号、历史、审计。移出俱乐部不影响其他俱乐部，也不撤销平台/联盟身份。
- **公会长转让**：正常俱乐部有且只有一名公会长；撤销现任前必须指定继任者；转让全有或全无；原公会长去留必须明确选择（改任管理员 / 移出），不自动安排；继任者原有的管理员职位要正确转换，转让后每人在该俱乐部只有一个生效职位。
- **界面**：中文、普通用户看得懂；显示当前职位、当前俱乐部、默认允许的操作、个人允许/禁止、最终生效权限、被上级限制的功能及原因；技术代码只放在「高级详情」。
- **安全**：撤销即时生效；职位与权限修改写不可删除审计；不能自我提权；不能改网址/请求绕过；俱乐部隔离；所有授权由 Worker 与数据库共同执行。
- **确认弹窗**：普通权限开关不弹窗（但有清晰状态反馈和审计）；撤销职位、公会长转让、批量移出、扩大敏感权限需明确确认。

## 4. 技术设计（各阶段共同遵守）

- **复用，不重写**：所有俱乐部授权仍只经过 `club_private.can(p_club, p_permission)`；平台授权仍只经过 `club_private.can_platform(p_permission)`；Worker 仍用 `routes` 表声明权限、默认拒绝；业务 RPC 继续 `club_private.require()`，RLS 继续 `readable_clubs()`。扩展这些函数，不在别处写角色判断。
- **权限登记**：新权限只在 `auth_permissions`（迁移）和 `apps/club/src/domain/permissions.ts` 登记，带中文说明。新增「不可委托」标记：带此标记的权限（如任命管理员、管理管理员权限）永远不能进入管理员的上限，也不能通过个人例外授予管理员。未来功能（如活动）按同样方式登记权限即可。
- **全平台默认权限** = 现有 `auth_role_permissions`（不另建）。俱乐部默认、职位上限、个人例外各用一张新表；个人例外记录设置层级（超级管理员 / 公会长）。没有任何设置时，计算结果必须与现在完全一致（用现有 SQL 测试证明）。
- **单职位**：保留现有主键 `(club_id, user_id, role)` 以保存历史，再加「每个 (club_id, user_id) 最多一条 active」的部分唯一索引；迁移前先按 §2-1 处理已有双职位。
- **超级管理员**仍以 `super_admin_active()` 为准（可信验证器 + aal2），不放宽。平台管理员用单独的判断：aal2 会话 + 本人已验证的 TOTP 验证器，不需要可信确认。
- **审计**：沿用现有俱乐部审计与平台审计触发器；新表都要接入，只能追加。
- **前后兼容**：每个迁移都必须让当前已部署的 Worker 继续工作（`pnpm test:compat`）。
- **多俱乐部（阶段 D）**：注意 Next.js 静态导出（`output: export`）不能为未知 ID 预生成动态路由，Cloudflare Workers 的资源路由也要兼容深层路径；方案需要说明选择和理由。俱乐部 ID 只是被每次请求校验的参数，不是权限来源。缓存作用域（`X-Club-Scope`）必须包含请求的俱乐部。「上次管理的俱乐部」只能作为导航偏好，不能作为授权依据。

## 5. 本地测试方法（不连接生产）

- Club 单元：`cd apps/club && node --test worker/*.test.mjs "src/**/*.test.mjs"`；类型 `npx tsc --noEmit -p .`；lint `npx eslint src`。
- SQL（本机没有 psql）：启动一次性容器 `docker run -d --rm --name squirrelapi-sqltest -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=squirrelapi_test -p 127.0.0.1:55432:5432 postgres:17`，然后用与 `scripts/test-db.mjs` 相同的拼接方式（bootstrap + 全部迁移 + 每个 suite 包在 savepoint 中）通过 `docker exec -i squirrelapi-sqltest psql --no-psqlrc -U postgres -d squirrelapi_test --quiet --set=ON_ERROR_STOP=1` 执行。用完 `docker stop squirrelapi-sqltest`。
- 浏览器：先 `pnpm --filter @squirrelapi/club build`，再 `pnpm test:e2e [文件]`。改了登录去向、页头或账户契约时必须跑**全部**浏览器测试（曾因只跑部分导致 CI 失败）；模拟的 `/api/account` 必须与真实 Worker 契约一致。

- 兼容：`pnpm test:compat`（已部署 Worker + 全部新迁移）。
- 机器上另有一个无关的 `fyp-supabase` 本地项目，**不要停止或修改它的容器**。
- 安全测试必须能在故意破坏对应检查后失败（至少抽查关键检查）。

### 阶段 B 记录（2026-11-02）

- **迁移** `20261101195800_club_permission_layers.sql`（只增不删，旧函数签名不变）：`auth_permissions.non_delegable`（只能标记、不能原地取消）；新表 `auth_role_cap_blocks`（职位上限：有行 = 该职位永远不能有此权限）、`club_role_permissions`（俱乐部默认，三态：无行 = 跟随全平台）、`club_permission_overrides`（个人三态，`set_by` = super_admin / owner）。三表 RLS、无任何客户端授权、平台审计触发器、禁止 truncate、写入触发器只接受俱乐部范围权限，俱乐部默认不能把不可委托权限给非公会长。全平台默认仍是 `auth_role_permissions`（触发器同样拒绝不可委托权限给非公会长）。新权限 `platform.permissions.manage`（仅超级管理员，阶段 E 不得授予平台管理员）。
